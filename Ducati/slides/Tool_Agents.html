Cosa sono i Tool?

Estendere le capacità dell'LLM oltre la sua knowledge base

Definizione

I tool consentono all'LLM di eseguire operazioni fuori dalla sua knowledge base: accedere a dati aggiornati, interrogare servizi o effettuare calcoli.

  • Informativi: ritornano dati (API, database)
  • Operativi: eseguono azioni (email, calcoli)
  • L'LLM decide autonomamente quando usarli
Punto Chiave

Il decoratore @tool genera automaticamente lo schema JSON richiesto dall'LLM, traducendo docstring e type hint.

Best Practice

Gestire bene le descrizioni aiuta il modello a scegliere il tool corretto.

05

RAG Agentico

L'agente decide quando e come cercare nei documenti

Cos'è?

Nel RAG agentico l'agente valuta se serve consultare i documenti, riformula la query se necessario e può ripetere la ricerca fino a ottenere un contesto sufficiente.

vs RAG Classico

Nel RAG classico ogni query genera sempre un embedding e una ricerca, anche per un semplice "Ciao!"

Benefici Principali
  • Efficienza: evita ricerche inutili
  • Copertura: query iterative e riformulazioni
  • Flessibilità: combina ricerca con altri tool

Esempio: Tool Meteo

Il decoratore @tool in azione

@tool
def get_weather(city: str, unit: str = "celsius") -> str:
    """Restituisce le condizioni meteo di una città italiana."""
    weather_data = {
        "bologna": {"temp": 22, "condition": "soleggiato"},
        "milano": {"temp": 18, "condition": "nuvoloso"},
        "roma": {"temp": 25, "condition": "sereno"},
    }

    city_lower = city.lower()
    if city_lower not in weather_data:
        return f"Città {city} non trovata nel database meteo."

    data = weather_data[city_lower]
    temp = data["temp"]
    if unit == "fahrenheit":
        temp = temp * 9 / 5 + 32

    return (
        f"A {city} ci sono {temp}°{'F' if unit == 'fahrenheit' else 'C'}, "
        f"cielo {data['condition']}."
    )
Schema Generato

datapizza-ai traduce automaticamente docstring e type hint in uno schema JSON compatibile con OpenAI function calling.

Output Esempio

"A Bologna ci sono 22°C, cielo soleggiato."

Esempio: Tool Calcolatrice

Eval controllato con funzioni matematiche consentite

import math

@tool
def calculate(expression: str) -> str:
    """Esegue calcoli matematici (pow, sqrt, trig)."""
    allowed_names = {
        "sqrt": math.sqrt,
        "pow": pow,
        "abs": abs,
        "round": round,
        "sin": math.sin,
        "cos": math.cos,
        "pi": math.pi,
    }

    try:
        result = eval(expression, {"__builtins__": {}}, allowed_names)
        return f"Il risultato di {expression} è {result}"
    except Exception as exc:
        return f"Errore nel calcolo: {exc}"
Perimetro sicuro
  • Nessun __builtins__ disponibile → impossibile eseguire codice arbitrario.
  • Whitelist di funzioni matematiche comuni.
  • Messaggi di errore controllati per migliorare il reasoning.
Uso tipico

Esegui calcoli intermedi all'interno del loop ReAct senza uscire dal contesto conversazionale.

Creare un Agente

Configurazione con datapizza-ai

from datapizza.agents import Agent
from datapizza.clients.openai import OpenAIClient

agent = Agent(
    name="weather_agent",
    system_prompt="""Sei un assistente che può fornire info meteo
    e fare calcoli matematici.""",
    client=OpenAIClient(api_key=api_key, model="gpt-4o-mini"),
    tools=[get_weather, calculate],
    max_steps=5,
)
Parametri Chiave
  • name: identificativo agente
  • system_prompt: istruzioni
  • tools: lista di tool
  • max_steps: limite iterazioni
💡 Tip

Usa stream_invoke() per vedere ogni step del ragionamento in tempo reale.

Testare l'agente

# Calcolo matematico

print(response.text)

# Ragionamento multi-step
response = weather_agent.run(
    "Se a Bologna ci sono 22 gradi, quanto fa il quadrato della temperatura?"
)

print(weather_agent.run("Ciao, come stai?").text)
Cosa monitorare
  • Che il modello risponda direttamente quando non serve un tool.
  • Che gli output dei tool vengano interpretati correttamente.
  • Che errori o città sconosciute vengano gestiti con grazia.

Tool: search_documents

Il cuore del RAG agentico

@tool
def search_documents(query: str, num_results: int = 3) -> str:
    """Cerca informazioni nei documenti Ducati indicizzati."""
    try:
        query_embedding = embedder.embed(query)
        results = vectorstore.search(
            query_vector=query_embedding,
            collection_name=COLLECTION,
            k=num_results,
        )

        if not results:
            return "Nessun documento trovato per questa ricerca."

        formatted = []
        for idx, chunk in enumerate(results, start=1):
            text = chunk.text[:500]
            suffix = "..." if len(chunk.text) > 500 else ""
            formatted.append(f"[Risultato {idx}]
{text}{suffix}")

        return "

".join(formatted)
    except Exception as exc:
        return f"Errore nella ricerca: {exc}"
Stack Tecnologico
Qdrant OpenAI Embeddings text-embedding-3-small
Flusso

Query → Embedding → Ricerca vettoriale → Top-K risultati → Formattazione

19

RAG Classico vs Agentico

Due approcci a confronto

📚 RAG Classico

Ogni query genera sempre embedding + ricerca

  • "Ciao!" → Cerca nel DB (inutile)
  • Costi elevati per query semplici
  • Nessuna riformulazione possibile
  • Un solo tentativo di ricerca

🤖 RAG Agentico

L'agente decide se e come cercare

  • "Ciao!" → Risposta diretta
  • Costi ottimizzati
  • Riformulazione query automatica
  • Iterazioni multiple se necessario

System Prompt dell'Agente RAG

Regole chiare per comportamento prevedibile

system_prompt = """
Sei un assistente esperto dei documenti aziendali Ducati.

REGOLE IMPORTANTI:
1. Usa search_documents SOLO per domande su Ducati
2. Per domande generiche rispondi SENZA usare il tool
3. Se non trovi info sufficienti, riformula la query
4. Basa le risposte sui documenti
5. Se non trovi nulla, dillo

Rispondi sempre in italiano.
"""
Anatomia del Prompt
  • Ruolo: definisce personalità
  • Regole numerate: chiarezza
  • Scope tool: quando usare/non usare
  • Lingua: output consistente

Best Practices

Consigli pratici per agenti efficaci

✅ Da Fare
  • Descrizioni tool chiare e dettagliate
  • Imposta max_steps ragionevole (5-10)
  • Usa stream_invoke() per debugging
  • Testa query che NON richiedono tool
  • Gestisci errori nei tool
⚠️ Da Evitare
  • Descrizioni vaghe o duplicate
  • System prompt senza regole chiare
  • max_steps troppo alto (spreco token)
  • Ignorare casi edge
  • Non monitorare latenza e costi

Key Takeaways

Cosa portare a casa

1. Tool = Estensione

I tool estendono l'LLM oltre la sua knowledge base. Il decoratore @tool elimina il boilerplate.

2. Agenti = Ragionamento

Il ciclo ReAct (Thought → Action → Observation) permette ragionamento iterativo su task complessi.

3. RAG Agentico = Efficienza

L'agente decide quando cercare, evitando ricerche inutili e permettendo riformulazioni.

4. Prompt = Controllo

Un system prompt ben strutturato garantisce comportamento prevedibile e consistente.

Appendice: Tool manuali

Quando serve definire schema e funzione a mano

def get_weather(city: str, unit: str = "celsius") -> dict:
    ... # restituisce dict con temperatura e condizione

weather_tool = {
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Restituisce il meteo di una città italiana",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string"},
                "unit": {
                    "type": "string",
                    "enum": ["celsius", "fahrenheit"],
                },
            },
            "required": ["city"],
        },
    },
}
Quando usarli
  • Framework diversi da datapizza-ai.
  • Necessità di pieno controllo sul JSON delle funzioni.
  • Compatibilità con API che si aspettano schema esplicito.
Consiglio

Riutilizza docstring e enum anche qui per mantenere le descrizioni allineate con i tool decorati.
