Dev Quickstart

Prima chiamata API

Guida pratica per chi non ha mai fatto una chiamata a un LLM via codice. Scegli la libreria che preferisci, tutte leggono la stessa OPENAI_API_KEY dall'ambiente.

Step 0 — Prima di tutto

Non mettere mai la chiave nel codice

Usa un file .env nella root del progetto. Le librerie OpenAI, LangChain, LlamaIndex e Datapizza AI la leggono tutte dalla stessa variabile d'ambiente.

1 — Installa dotenv

pip install python-dotenv

pip install python-dotenv

Libreria standard per caricare variabili da file .env nell'ambiente Python. Un solo comando, nessuna dipendenza pesante.

2 — Crea il file .env

Nella root del progetto

# file: .env  (nella stessa cartella del tuo script)

OPENAI_API_KEY=sk-proj-XXXXXXXXXXXX

# il nome della variabile è esatto — non cambiarlo
# niente virgolette, niente spazi attorno all'=

La chiave ti viene consegnata all'avvio della challenge. Budget: €80 per team.

3 — Aggiungi .env al .gitignore

Mai committare la chiave

# file: .gitignore

.env
__pycache__/
*.pyc

Se la chiave finisce su GitHub, potrebbe essere un bel problema, aggiungi un file .gitgnore così formattato.

4 — Carica le variabili in Python

Chiama load_dotenv() all'inizio di ogni script

from dotenv import load_dotenv
import os

load_dotenv()  # legge il file .env e carica le variabili nell'ambiente

# leggi la chiave in una variabile da passare ai client delle librerie
key = os.getenv("OPENAI_API_KEY")
print(f"Chiave caricata: {key[:8]}...")  # stampa solo i primi 8 caratteri per verifica

Struttura file consigliata: 

my-project/
├── .env              ← chiave API (NON committare)
├── .gitignore        ← contiene ".env"
├── main.py           ← il tuo codice (load_dotenv() in cima)
└── requirements.txt  ← openai  python-dotenv  ...

from dotenv import load_dotenv
import os
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

load_dotenv()
key = os.getenv("OPENAI_API_KEY")

llm = ChatOpenAI(model="gpt-5.4-mini", api_key=key)

prompt = ChatPromptTemplate.from_messages([
    ("system", "Sei un esperto AI Governance bancaria. Cita sempre i nodi tassonomici ABI Lab."),
    ("human", "Sistema AI:\n{sistema}\n\nDomande Checklist più critiche e perché:")
])

chain = prompt | llm

result = chain.invoke({
    "sistema": "ChatBanca su MA A.1.5, dati MI 2.1 — chatbot retail Internet Banking"
})
print(result.content)

// Consigli pratici per l'hackathon
BUDGET Sviluppa sempre con gpt-5.4-mini — costa ~5× meno di gpt-5.5. Passa al modello potente solo per rifinire l'output finale e la demo. €80 bastano se li gestisci bene

Scenario A

Consorzio di banche — Capogruppo BancaCoop S.p.A.

File: Dataset_ScenarioA_Consorzio.xlsx

Un capogruppo di gruppo bancario cooperativo gestisce centralmente 2 sistemi AI distribuiti a circa 200 affiliate. La governance è stata formalizzata una sola volta a livello centrale, ma ogni affiliata mantiene operatività e responsabilità proprie.

Domanda operativa: quali responsabilità restano in capo alla capogruppo, quali ricadono sulle affiliate e quali KPI non sono calcolabili localmente per limiti di perimetro informativo?

5 sheet nel file
  • SCENARIO — contesto della banca fittizia e sfida operativa.
  • SISTEMI_AI — inventario dei sistemi con rischio e stato della governance.
  • MAPPING_ARCHITETTURALE — collocazione dei sistemi nelle 5 tassonomie.
  • CHECKLIST_GOVERNANCE — stato corrente delle risposte e gap rilevati.
  • KPI_SELEZIONATI — foglio da completare con i KPI pertinenti.
Il sistema prodotto durante l'hackathon potrebbe aiutare a...
  • Disaggregazione delle responsabilità tra capogruppo, affiliata o entrambi.
  • Valutazione della calcolabilità dei KPI a livello locale o aggregato.
  • Lettura dei nodi condivisi e dei nodi locali nell'architettura.
  • Raccomandazioni operative per colmare la zona grigia di responsabilità.

Vista attesa: matrice RACI capogruppo↔affiliata per ogni sezione della checklist, con evidenza dei KPI non calcolabili dall'affiliata.

Scenario B

Fusione bancaria — BancaAlfa S.p.A. + BancaBeta S.p.A.

File: Dataset_ScenarioB_Fusione.xlsx

Due banche di pari taglia entrano in fusione con portfolio AI diversi, livelli di governance differenti e più sistemi che svolgono funzioni analoghe su architetture distinte.

Domanda operativa: come confrontare i due portfolio sulle stesse tassonomie, identificare sistemi equivalenti o orfani e costruire una raccomandazione di integrazione per il nuovo gruppo?

9 sheet nel file
  • SCENARIO — contesto della fusione e vincoli di integrazione.
  • SISTEMI_AI_BancaA / _BancaB — inventario dei due portfolio.
  • MAPPING_ARCHITETTURALE_BancaA / _BancaB — confronto sulle tassonomie.
  • CHECKLIST_GOVERNANCE_BancaA / _BancaB — stato della governance per ciascuna banca.
  • EQUIVALENZE_DA_DERIVARE e CONSOLIDAMENTO — supporto alla mappa di integrazione.
Il sistema prodotto durante l'hackathon potrebbe aiutare a...
  • Derivazione delle coppie di sistemi equivalenti e dei sistemi orfani.
  • Raccomandazioni tenere/dismettere con motivazione architetturale.
  • Lettura dei gap ereditati dal portfolio post-fusione.
  • Proposta di governance unificata per il nuovo gruppo.

Vista attesa: confronto A↔B tra sistemi equivalenti, con delta di governance e raccomandazione di consolidamento.

Una banca commerciale con 12 sistemi AI in produzione ha ricevuto rilievi formali da vigilanza su specifici sistemi, con scadenze a 30, 60 e 90 giorni e rischio sanzionatorio in caso di mancato adeguamento.

Domanda operativa: come tradurre i rilievi in azioni architetturali concrete, valutarne la fattibilità nei tempi e costruire una roadmap di remediation con priorità forzata?

7 sheet nel file
  • SCENARIO, SISTEMI_AI, MAPPING_ARCHITETTURALE, CHECKLIST_GOVERNANCE.
  • RILIEVI — verbale ispettivo con input e colonne di output da completare.
  • ROADMAP_REMEDIATION — sprint 30/60/90 giorni da strutturare.
  • KPI_SELEZIONATI — monitoraggio della remediation per sistema.
Il sistema prodotto durante l'hackathon potrebbe aiutare a...
  • Traduzione dei rilievi in azioni architetturali puntuali.
  • Stima di effort, sistemi correlati impattati e fattibilità entro deadline.
  • Sequenziamento dei rilievi in sprint con dipendenze esplicite.
  • Reporting esecutivo per regolatore e comitati interni.

Vista attesa: roadmap di remediation per deadline, severità e rischio sanzionatorio.
