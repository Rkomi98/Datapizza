Tornare indietro con git, senza panico

"Tornare indietro" è un'espressione comoda che nasconde almeno sei operazioni diverse tra loro, ognuna con un raggio d'azione preciso: correggere un file, togliere qualcosa dallo staging, sostituire l'ultimo commit, registrare un'inversione pubblica, spostare il branch locale, recuperare un commit che sembrava perso.

Il punto di partenza giusto non è mai il comando che ricordi a memoria, ma la domanda: su cosa sto agendo, e quella cosa è già visibile a qualcun altro? Working directory, staging e storia locale sono territorio tuo, puoi correggere il tiro liberamente. Nel momento in cui un commit è stato pubblicato, la stessa mossa cambia significato: da correzione privata diventa un problema che riguarda chiunque abbia già fatto pull.

Modello mentale

Le quattro zone di git

Ogni comando di questa famiglia agisce su un confine preciso tra due zone. Individuare il confine giusto è già metà del lavoro.

Zona 1

Working directory

I file sul disco, con le modifiche non ancora selezionate per il prossimo commit.

git add
⇄
git restore <file>
Zona 2

Staging area

L'anticamera del commit: qui vive esattamente ciò che finirà nella prossima fotografia della storia.

git commit
⇄
git restore --staged
git reset / --amend
Zona 3

Repository locale

La cronologia dei commit sul tuo branch: ancora soltanto sul tuo computer, riscrivibile senza chiedere permesso a nessuno.

git push
⇄
git revert <hash>
Zona 4

Repository remoto

La cronologia condivisa. Da qui in avanti, ogni riscrittura è una notizia che riguarda tutti i cloni, non solo il tuo.

Tasca laterale, da working dir + staging
git stash push → git stash pop
git reflog Non è una quinta zona ma un registratore che gira dentro alla zona 3: annota ogni spostamento del branch e di HEAD, commit, reset, amend, checkout, rebase. Non viene mai pubblicato e non è eterno, ma per un certo periodo è la rete di sicurezza che ti permette di ritrovare qualcosa che sembrava sparito.

La regola pratica che vale la pena portarsi a casa è più semplice di quanto sembri dal numero di comandi coinvolti. Finché ti muovi tra working directory, staging e commit locali non ancora pubblicati, sei nel tuo territorio: restore, reset e amend correggono il tiro senza conseguenze per nessun altro. Nel momento in cui un commit è arrivato sul remoto ed è stato tirato giù da qualcun altro, cambia il verbo giusto: non si cancella più, si compensa. Ed è lì che entra in scena revert, l'unico dei cinque pensato apposta per la storia già pubblica.

Se qualcosa va storto e sembra irrecuperabile, prima di allarmarti vale la pena controllare il reflog: git raramente butta via davvero qualcosa, semplicemente smette di indicarlo.
